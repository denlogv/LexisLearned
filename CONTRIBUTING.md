# Contributing to LexisLearned

Thanks for your interest! This page covers how to build the app, run the tests and find your way around the code.

## Setup

- JDK 17 to 21. CI builds with 21, JDK 27 does not build the `detekt-rules` module (Java and Kotlin end up with different JVM
  targets), and recent Android Studio versions bundle a newer JDK, so install JDK 21 (for example Temurin or JetBrains Runtime 21)
  and point `JAVA_HOME` at it.
- Android SDK with compile SDK 37.

```bash
./gradlew testDebugUnitTest assembleDebug
```

## Code quality

Formatting, linting and coverage are checked automatically for every pull request, and you can run the same checks locally:

```bash
./gradlew ktlintFormat                                   # fix formatting (ktlint)
./gradlew ktlintCheck detekt :detekt-rules:test testDebugUnitTest jacocoTestCoverageVerification lintDebug assembleDebug
```

The rules (documented code, small functions and classes, no logic in composables, 80% line coverage) are listed in
[AGENTS.md](AGENTS.md); they apply to human and AI-written changes alike.

## Tests

The unit tests use only generated placeholder data, so the repository never needs real book content.

```bash
./gradlew testDebugUnitTest
```

An optional smoke test helps when working on the EPUB reader. It is skipped unless you point it at a file:

```bash
EPUB_SAMPLE=/path/to/book.epub   ./gradlew testDebugUnitTest --tests '*EpubSmokeTest*' -i   # prints how the book is split
```

`samples/` holds a demo deck (`demo-everyday-english.lexis`) and a tiny original EPUB (`lighthouse-sample.epub`, regenerated by `samples/make_sample_epub.py`). Please do not add copyrighted material to the repository.

## Project layout

```
app/src/main/java/dev/denlogv/lexislearned/
  domain/   model, scheduler, session planner, answer matching (pure Kotlin, unit-tested)
  format/   DeckFormat interface; .lexis (JSON) implementation
  data/     Room database, repository, settings and encrypted API-key storage
  epub/     EPUB reader: table of contents, parts, sections, boilerplate detection
  ai/       LLM clients (Anthropic, OpenAI and compatible servers), prompts per level, deck generation, pausing and resuming
  service/  the foreground service that keeps a generation alive in the background, and its notifications
  ui/       Jetpack Compose screens (library, book, part, chapter, study, EPUB, settings)
detekt-rules/  the project's own detekt rule (documentation completeness) and its tests
samples/    a demo deck and a tiny original EPUB
docs/       screenshots, release instructions, AI-development process, architecture decision records (docs/adr)
tools/      helper scripts (commit checks, release keystore)
```

## Good to know

- **Session logic** lives in `domain/SessionPlanner.kt`. It only knows card ids, so it is easy to test; the study view model in `ui/study/` applies its steps and saves results.
- **Adding a file format:** implement `DeckFormat` (see `format/NativeFormat.kt`) and add it to `FormatRegistry`.
- **Database changes** need a Room migration (see `data/Migrations.kt`); progress must survive an update.
- **Pause and resume:** `GenerationManager` publishes a `GenState`; a run that does not finish every chosen section ends in `Paused`, and `JobJournal` keeps the book and the sections still to do in files (`FileJobStore`) so `restore()` can bring a paused run back on the next launch. Only the user ends a pause (`resume()` or `discard()`).
- **Background work:** `GenerationManager` asks a `KeepAlive` to hold the process when a run starts; `ServiceKeepAlive` starts `GenerationService`, a foreground service that `GenerationWatcher` drives from the generation state. Keep decisions in the watcher so they stay testable.
- **Prompts** for each level are in `ai/Prompts.kt`. The reply format in the fixed header must stay in sync with the parser in `ai/CardGenerator.kt`.
- **EPUB structure detection** is heuristic (`epub/EpubStructure.kt`, `epub/EpubReader.kt`). If a book is split badly, a failing test with generic titles and word counts is the most useful report.

## Submitting changes

Open an issue first for larger changes. Keep pull requests small enough to review in one sitting, add or update unit tests where
logic changes, and make sure the checks in [Code quality](#code-quality) pass.

The history of `main` is curated: pull requests are merged with *rebase and merge*, so every commit you submit ends up on `main`.

- One logical change per commit; each commit builds and passes the checks on its own.
- [Conventional Commits](https://www.conventionalcommits.org/) (`feat(ui): add ...`), with a body that explains *why* for
  `feat`, `fix`, `refactor` and `perf`.
- No `fixup!`, `squash!` or "address review" commits left over: fold fixes into the commit they belong to
  (`git commit --fixup <sha>`, then `git rebase -i --autosquash origin/main`).
- Check your branch before pushing:

```bash
tools/check-commits.sh origin/main..HEAD      # messages follow the rules
tools/verify-commits.sh origin/main..HEAD     # every commit builds and passes (slow)
```

The pull request template asks whether AI was involved and what was verified. Answer honestly; it is not a judgement, it tells
the reviewer where to look. The reasoning behind larger decisions is in [docs/adr](docs/adr/README.md). Report security problems
privately, see [SECURITY.md](SECURITY.md).

## Repository settings (maintainers)

Some settings live on GitHub rather than in the repository. Apply them once after creating it.

- **Branch rules for `main`:** import [`.github/rulesets/main.json`](.github/rulesets/main.json) under *Settings → Rules → Rulesets*.
  It requires a pull request with resolved conversations, the status checks (`Format, lint, tests and coverage`,
  `Commit messages`, `CodeQL`, `Dependency review`, `Secret scan`) on an up-to-date branch, linear history, and it blocks force
  pushes and deletion. It asks for no approvals because one maintainer cannot approve their own pull request; raise
  `required_approving_review_count` once there is a second reviewer. If you rename a workflow job, update the ruleset.
- **Merge method:** allow only *Rebase and merge* (turn off merge commits and squash merging under *Settings → General*).
  Squashing would hide messy branch history instead of preventing it and would turn a large change into one commit that cannot
  be reviewed piece by piece, so commits are curated before the merge instead (see above). Rebase-and-merge rewrites the commits,
  so requiring an up-to-date branch keeps the merged commits equal to the tested ones.
- **Code security:** enable the dependency graph, Dependabot alerts and security updates, secret scanning with push protection,
  and private vulnerability reporting (`SECURITY.md` relies on it).
- **Actions:** default workflow token permission "Read repository contents". Every action in the workflows is pinned to a commit.
- **Release secrets:** `RELEASE_KEYSTORE_BASE64`, `RELEASE_KEY_ALIAS`, `RELEASE_KEYSTORE_PASSWORD` and, if it differs,
  `RELEASE_KEY_PASSWORD` (see [docs/RELEASING.md](docs/RELEASING.md)).

## AI-assisted development

Much of this code is written by AI coding agents (Claude Code) under the direction of a human maintainer, who specifies the
features, answers design questions, tries the app on an emulator and a phone, and decides how closely to review each change.
Pull requests say whether AI was involved, what was verified and by whom, and how deeply the code was reviewed; nothing in this
repository claims more review than the pull request says.

- **One instruction file.** [`AGENTS.md`](AGENTS.md) holds the commands and rules that agents (and people) work under. It is the
  open convention that most coding agents read, and it is deliberately the only AI-specific file.
- **Rules are enforced by tools, not by prompts.** CI runs ktlint, detekt with a custom rule that requires KDoc on every
  parameter, unit tests with an 80% line-coverage gate, Android lint, CodeQL, dependency review, secret scanning and a check of
  every commit message, for every pull request and again before a release.
- **What tools cannot check** is left to people: whether commits are really atomic and well explained, whether the tests test
  the right thing (an AI can encode the same misunderstanding in code and tests, and coverage measures executed lines, not
  correctness), whether the agent followed `AGENTS.md` honestly, and product judgement. How much of a pull request is reviewed
  is the maintainer's choice and is stated in the pull request; a review comment is the remedy when an agent cut a corner.
- **Secrets stay out of reach.** The release keystore password comes from the Keychain or CI secrets and is never printed or read
  by an agent. Releases publish a checksum and a build provenance attestation.
